## Context

当前后台已经完成了基础管理能力搭建，但从代码结构和交互表现看，仍处于“以页面为单位独立完成功能”的阶段：

- 后台页面普遍直接在页面内完成数据加载、筛选、列表和弹层逻辑，缺少统一的容器与模式抽象。
- 表格、工具栏、筛选、状态徽标、空状态、加载态在不同页面之间实现风格不一致。
- `/write` 已有更细的编辑器交互，但 `/admin` 作为管理中枢还没有形成围绕“待处理动作”的操作台模型。

本次设计的目标不是单纯“换皮”，而是借重构 UI 的机会把后台信息架构和高频操作流整理清楚。

## Goals / Non-Goals

- Goals:
  - 建立统一后台视觉系统和组件样式基线
  - 提升文章、评论、项目、设置等页面的信息可读性和操作效率
  - 强化 `/admin` 与 `/write` 的联动，形成更顺手的内容管理闭环
  - 在不增加复杂依赖的前提下，让后台具备更成熟的产品感
- Non-Goals:
  - 不做后端模型级重构
  - 不改公开站点主视觉
  - 不为未来不确定场景预埋过多抽象

## Current Findings

### 1. 布局层问题

- `app/admin/layout.jsx` 目前只是“左侧边栏 + 顶栏 + 主内容区”的基础壳，没有后台专属主题变量，也没有为移动端、内容宽度、页面节奏做统一约束。
- `AdminSidebar` 采用简单折叠模式，但缺少当前上下文、快捷动作、品牌识别和次级说明；交互更像开发期导航而不是管理工作台。
- `AdminHeader` 仅显示页面标题和登出，信息密度偏低，无法承载全局搜索、快捷入口、上下文提示等高价值元素。

### 2. 页面层问题

- 仪表盘页仍以基础统计卡片为主，缺乏“待处理评论/最新草稿/项目状态”的聚合视图。
- 文章、评论、项目页都使用了偏原始的表格/列表实现，高频操作虽可用，但识别成本高，缺少分组、骨架、批量过滤和更清晰的行级动作。
- 设置页是典型长表单，分组信息弱，主次关系弱，不适合作为持续维护的控制台页面。

### 3. 视觉层问题

- 后台没有独立的设计 token，颜色、边框、背景、阴影、交互反馈零散写在页面里。
- 当前样式普遍是“白卡片 + 灰边框 + 玫红按钮”，可用但不够稳定，无法支撑更复杂的后台操作场景。
- 和 `/write` 相比，后台缺少清晰的空间感和工作流导向。

### 4. 工作流问题

- `/write` 已支持自动保存和草稿箱入口，但后台文章页仍以传统列表为主，没有围绕“继续编辑、处理修改稿、切换分类、查看发布态”的完整联动设计。
- 评论与项目管理页动作虽完整，但缺少统一的反馈模型和视觉语义。

## Decisions

### Decision 1: 建立后台专属设计 token 与样式层

- 在 `app/globals.css` 中新增 `admin-*` 主题变量与基础样式类，而不是继续在各页面散落 Tailwind 原子类。
- 颜色方向采用“暖白 + 石墨 + 酒红/铜金点缀”的编辑工作台风格，避免通用后台模板的廉价感，同时与博客站点气质保持弱关联。
- 为卡片、表格、工具栏、筛选胶囊、状态徽章、抽屉、弹层统一定义边框、阴影、圆角、背景和焦点态。

Why:

- 统一 token 才能避免后续每个页面继续各写各的。
- 视觉目标是“精致编辑台”，不是通用 SaaS 模板。

### Decision 2: 后台首页改成工作台模型

- `/admin` 首页采用三段结构：
  - 顶部概览：关键指标与系统状态
  - 中部待处理：待审核评论、最新草稿、最近修改
  - 底部动态：最新评论与快捷入口

Why:

- 管理后台首页的价值不在“展示统计”，而在“告诉管理员下一步该做什么”。

### Decision 3: 列表页统一为“工具栏 + 主列表 + 侧向详情/状态区”模式

- 文章、评论、项目页都统一为：
  - 页头说明
  - 筛选/搜索/快捷操作工具栏
  - 主列表容器
  - 空状态 / 加载态 / 行级动作一致化
- 评论页优先考虑“查看 + 审核 + 标记垃圾”的快速决策流。
- 文章页优先考虑“继续编辑 + 分类调整 + 状态识别 + 草稿/发布切换”的内容运营流。

Why:

- 页面模式统一之后，维护成本更低，用户认知负担也更低。

### Decision 4: 项目与设置页从“长表单”升级为“分区控制台”

- 项目列表保留表格效率，但补上更强的精选、状态和封面信息层级。
- 项目编辑页改为分块表单，突出封面、状态、精选位和外链管理。
- 设置页改为卡片分区 + 说明文案 + 明确保存反馈，弱化一次性大表单感。

Why:

- 当前页面已经不只是 CRUD，而是带内容运营属性的后台。

### Decision 5: `/write` 与后台的工作流联动继续增强，但控制在低风险范围

- 保留现有 `/write` 能力，不重做编辑器。
- 重点增强后台与写作页之间的快捷入口和状态认知一致性。
- 若需要新增 `/write` 快捷操作，只做轻量联动，不在本轮扩大为编辑器架构重写。

Why:

- 用户当前核心诉求是后台管理界面体验与管理效率，不是重写写作器。

## Risks / Trade-offs

- 风险：页面级 UI 重构范围较大，容易在多个后台页面之间来回改样式。
  - Mitigation: 先抽统一容器与样式 token，再逐页迁移。
- 风险：现有页面大多是 client component，重构时容易把视觉变更和逻辑变更混在一起。
  - Mitigation: 优先做结构和样式整理，尽量少改数据接口。
- 风险：后台样式若和公开站点过度绑定，会增加未来维护负担。
  - Mitigation: 保持“气质关联”，但 token 独立。

## Implementation Plan

### Phase 1: 视觉与布局底座

- 增加后台设计 token 和基础样式类
- 重构 `AdminLayout`、`AdminSidebar`、`AdminHeader`
- 完成登录页视觉升级

### Phase 2: 仪表盘与文章管理

- 重构 `/admin`
- 重构 `/admin/posts`
- 补齐后台文章页的状态表达、快速操作和空状态

### Phase 3: 评论与项目管理

- 重构 `/admin/comments`
- 重构 `/admin/projects`
- 重构 `/admin/projects/[id]`

### Phase 4: 设置页与 `/write` 联动

- 重构 `/admin/settings`
- 轻量优化 `WritePageV2` 的后台入口和状态联动

## Verification Strategy

- 运行 `pnpm lint`
- 运行 `pnpm build`
- 手动验证：
  - `/admin/login`
  - `/admin`
  - `/admin/posts`
  - `/admin/comments`
  - `/admin/projects`
  - `/admin/projects/[id]`
  - `/admin/settings`
  - `/write`
- 验证移动端和桌面端布局是否都可用

## Open Questions

- 后台首页是否要纳入“最近修改中的项目/文章”混合流，还是只保留文章与评论？
- 本轮是否接受对 `/write` 顶部工具栏做同步风格升级，还是仅保留跳转联动？
